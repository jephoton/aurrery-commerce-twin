# Render Free + Turso deployment and ledger recovery

<!-- Generated operational handoff. Offline preparation is not deployment acceptance. -->

Use one Render **Free** Node 24 web service and one free Turso **libSQL** database. Keep deployments manual until acceptance. There is no disk, paid database, alternate hosting/storage platform, local-first replica or automatic provider fallback. `render.yaml` pins `>=24.0.0 <25.0.0`, installs development build tools with `npm ci --include=dev`, builds the pure worker before Next, starts with the assigned `PORT` (local default 3001), and checks `/api/health`. No runtime ledger, provider or PayPal access is required during build/prerender.

## Administrator access and uncertain executions

Use the dashboard's **Administrator access** password form over the configured HTTPS origin. Sessions last two hours in Secure, HttpOnly, SameSite=Strict `__Host-aurrery-admin` cookies. The authoritative ledger stores only hashes/fingerprints. **Sign out** revokes the session. Rotate `ADMIN_PASSWORD` privately and restart/redeploy to invalidate sessions bound to its old fingerprint; rotate `HOSTED_SECRET` to change session/admission HMAC authority. Never share cookies or paste passwords into a CLI argument. All visitors still share the conservative client admission bucket; arbitrary forwarded headers cannot increase allowance (effective hosted agent capacity is three total runs/hour, also bounded by global/day and provider limits).

Approval, execution, revert and administrator reset require their existing separate exact-action confirmation. Backup/import never creates a new approval. An `executing` proposal or unresolved target claim can represent a completed PayPal write whose acknowledgement was lost. Inspect authoritative execution/observation/audit records and current PayPal **before** any further mutation; do not clear claims, change request IDs, force statuses, run reset or replay an old approved action as a shortcut. A request that timed out may already have committed. There is no automatic query/write retry or PayPal replay on an ambiguous outcome. A revert is a new separately approved action; a reset is restricted and explicitly confirmed.

## Consistent private backups

For a **local SQLite source**, use its online backup API through the helper; the source is opened read-only and is never migrated. An active WAL contains committed pages missing from a raw copy of `ledger.sqlite`. Never copy just that file while it is open, delete its WAL or force a checkpoint as a backup method.

```bash
npm run --silent ledger:export -- --source <absolute-existing-local-ledger.sqlite> --output <absolute-new-private-backup.sqlite>
npm run --silent ledger:import -- --dry-run --source <absolute-new-private-backup.sqlite>
```

For the **authoritative Turso source**, privately set explicit `LEDGER_BACKEND=turso`, `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` and no `LEDGER_PATH`. Then:

```bash
npm run --silent ledger:export -- --output <absolute-new-private-backup.sqlite>
```

Without `--output`, the helper uses a unique `data/ledger-backup-<uuid>.sqlite` in the ignored local directory. Locate it privately; logs deliberately contain no output path or private rows/tokens. Use the documented `npm run --silent` form to suppress npm's own command/argument echo, or invoke the script directly with `node --import=tsx --conditions=react-server scripts/export-ledger.ts`. Run `git check-ignore` on intended repository-local backups before retaining them. Custom destination directories must already exist. Use a private directory/account ACL on Windows and suitable permissions elsewhere; the helper requests private directory/file modes on systems that support them. The SQLite backup contains sensitive authority including hosted session fingerprints; keep it outside shared/public directories and back it up privately. The console manifest contains only schema/table hashes, counts and total rows; retain it privately with the matching backup.

Remote export opens an **existing canonical source without schema initialization or migration**. It takes one checked primary write transaction for a consistent snapshot, performs canonical schema/integrity/FK/record validation, and reads every canonical table in fixed order with bounded pages. No source rows are changed. The write transaction can briefly block competing writers; keep exports operator-initiated. It includes proposals of every supported action/status, exact actions/hashes/approval metadata, executions, unresolved claims, observations, webhook deduplication facts, discount episodes, settings, audits, classifier caches, sessions, quotas and `sqlite_sequence`. Pilot insertion order is preserved; sequence values and all manifest counts/hashes are verified after reconstruction. It uses the same snapshot application/record validation as import and a read-only importer dry-run before publishing a complete local file. Legacy local optional tables remain compatible with the existing importer; a noncanonical remote source is refused rather than repaired.

Output creation is exclusive: existing files are never overwritten. Only the helper's owned temporary directory is removed. A failure/ambiguous commit never reports success or a partial manifest; inspect authority and the private output before retrying. There is no public export route and no provider/PayPal request. [Turso's basic CLI export](https://docs.turso.tech/cli/db/export) warns that its snapshot can omit recent changes, so it is not this payment authority backup procedure. These semantics are tested with temporary local SQLite/libSQL files and fake failures; live Turso backup acceptance remains pending.

## Recovery into an empty authoritative target

Keep the old authority and backup immutable. Stop the app and other writers, choose the intended free empty replacement libSQL target, and privately configure its URL/token. Do not visit the app or allow webhook delivery before import. Dry-run the exact backup, apply it with `ledger:import`, compare all manifest fields and then explicitly select the recovered target for the service. Import refuses nonempty targets and cannot merge divergent histories. No unsupported platform restore command is assumed. The snapshot itself contains no instruction to approve or execute anything.

An older backup may omit successful PayPal writes, genuine events, more recent approvals, claims or session revocation. Reconcile current Sandbox subscription state, provider delivery history and retained authority with the restored records before re-enabling any execution. Retain unresolved claims and reconcile approved actions as potentially stale; never replay them merely because the older snapshot says approved. Rotate administrator/session secrets after restoring an older session store. If authority cannot be established, leave execution disabled and investigate. Explicit restore and successful hash verification establish a ledger copy, not PayPal equivalence, a fresh merchant approval or replay authorization.
